# 医疗知识库处理流程与章节清洗说明

## 1. 文档目标

本文档专门说明 `xbl-home` 医疗知识库小程序从书籍导入到页面展示的完整处理链路，并重点解释章节提取和噪音清洗逻辑。

代码主入口：

- Controller：`src/main/java/com/xu/home/controller/blog/MedicalKnowledgeController.java`
- Service 接口：`src/main/java/com/xu/home/service/medical/MedicalKnowledgeService.java`
- Service 实现：`src/main/java/com/xu/home/service/medical/impl/MedicalKnowledgeServiceImpl.java`
- 数据库脚本：`src/main/resources/liquibase/db/2026/2026-medical-knowledge-tables.xml`
- 前端页面：`xbl-web/src/views/apps/MedicalKnowledgeApp.vue`

当前实现的核心思路是：

1. 先把书籍接入系统
2. 再把文件解析成文本
3. 再把文本清洗并整理成章节
4. 一章生成一条 `medical_knowledge_chunk`
5. 按章节调用 AI 抽取知识条目
6. 条目和证据分别入库
7. 前端分页展示知识并支持查看原文依据

## 2. 总体流程

### 2.1 用户发起导入

前端有两种导入方式：

- 本地路径导入：`POST /blog/medical/knowledge/source/local/import`
- 上传文件导入：`POST /blog/medical/knowledge/source/upload`

本地路径导入适合服务端能直接访问文件的场景，上传导入适合用户从浏览器选择文件。

Controller 只做三件事：

- 读取当前账号
- 接收前端参数
- 调用 `MedicalKnowledgeService`

真正的处理逻辑都在 `MedicalKnowledgeServiceImpl`。

### 2.2 后端校验文件

本地导入方法是 `importFromLocal`。

它会执行：

- 判断路径是否为空
- 调用 `resolveAndValidateLocalPath` 判断路径是否存在
- 读取 `medical.knowledge.allowed-local-roots` 白名单
- 如果配置了白名单，则导入路径必须在白名单范围内
- 调用 `collectSupportedFiles` 收集文件
- 只接受 `pdf`、`txt`、`docx`

上传导入方法是 `importFromUpload`。

它会执行：

- 判断上传文件是否为空
- 判断原始文件名是否为空
- 识别文件扩展名
- 校验是否属于支持格式
- 创建上传目录
- 清理文件名中的非法字符
- 将文件保存到服务端

这一步不是文本处理，而是保证后续任务拿到的是一个可读、格式明确、路径安全的文件。

### 2.3 先建来源和任务，再异步处理

每导入一本书，系统先写两类记录。

`medical_knowledge_source` 表表示一本书，写入方法是 `createSource`。

主要字段：

- `account`：当前账号
- `source_name`：书名或文件名
- `source_type`：来源类型，`1` 本地路径，`2` 上传文件
- `file_format`：文件格式
- `file_size`：文件大小
- `file_hash`：文件哈希
- `local_path`：本地原始路径
- `storage_path`：服务端实际读取路径
- `parse_status`：解析状态
- `extract_status`：提取状态
- `chapter_count`：章节数
- `chunk_count`：章节块数
- `knowledge_count`：知识条目数

`medical_knowledge_task` 表表示一次处理任务，写入方法是 `createTask`。

主要字段：

- `source_id`：对应书籍
- `task_type`：任务类型，`1` 导入，`2` 重新提取
- `task_status`：任务状态
- `model_name`：AI 模型名
- `prompt_version`：提示词版本
- `result_message`：任务进度消息

建完记录后，系统调用 `startAsyncTask` 提交异步任务。前端接口会很快返回，不等待整本书解析和 AI 提取完成。

### 2.4 异步主流程

异步任务入口是 `processSource`。

执行顺序如下：

1. 调用 `getOwnedSource` 校验来源属于当前账号
2. 读取任务记录
3. 任务状态改为运行中
4. 来源解析状态改为运行中
5. 调用 `parseDocument` 解析文件
6. 调用 `buildChunks` 生成章节块
7. 调用 `persistChunks` 保存章节块
8. 更新来源解析成功、提取运行中
9. 调用 `extractKnowledgeItems` 按章节提取知识
10. 更新来源知识数量和提取成功状态
11. 更新任务成功状态

如果中间异常：

- 任务状态改为失败
- 来源解析和提取状态改为失败
- `error_message` 保存错误信息

## 3. 文件读取和初步分段

### 3.1 统一入口 `parseDocument`

`parseDocument` 按文件格式分发：

- `pdf` 调用 `parsePdf`
- `txt` 调用 `parseTxt`
- `docx` 调用 `parseDocx`

三个方法最终都会返回 `ParsedDocument`。

`ParsedDocument` 包含：

- `title`：文档标题
- `segments`：初步分段列表

注意：这里的 `segments` 还不是最终入库的 chunk。它只是解析阶段得到的临时分段，后面还要经过章节归并和清洗。

### 3.2 PDF 读取

PDF 读取方法是 `parsePdf`。

执行方式：

1. 使用 PDFBox `Loader.loadPDF` 打开文件
2. 使用 `PDFTextStripper` 逐页提取文本
3. 每页调用 `cleanRawText` 做基础清理
4. 调用 `findHeadingFromText` 尝试从页面中找到章节标题
5. 调用 `removeLeadingHeading` 去掉正文开头重复出现的标题
6. 将每页包装成一个 `ParsedSegment`
7. 调用 `normalizeChapterSegments` 把页面分段合并成章节

PDF 的难点是它没有天然章节结构。代码只能先按页取文本，再根据标题特征和噪音过滤规则推断章节。

### 3.3 TXT 读取

TXT 读取方法是 `parseTxt`。

执行方式：

1. 调用 `readTextWithFallback` 读取全文
2. 依次尝试 `UTF-8`、`GBK`、`UTF-16LE`
3. 调用 `splitPlainTextSegments` 按行扫描
4. 遇到章节标题就开启新分段
5. 普通行追加到当前分段
6. 调用 `normalizeChapterSegments` 做最终章节规整

TXT 的章节识别主要依赖每一行是否满足标题模式。

### 3.4 DOCX 读取

DOCX 读取方法是 `parseDocx`。

执行方式：

1. 使用 POI 打开 `XWPFDocument`
2. 遍历每个 `XWPFParagraph`
3. 调用 `cleanInlineText` 清理段落空白
4. 如果段落像标题，则开启新章节
5. 如果段落不是标题，则追加到当前章节
6. 调用 `normalizeChapterSegments` 做最终章节规整

DOCX 比 PDF 稳定一些，因为 Word 文档天然有段落结构。

## 4. 章节提取和章节块入库

### 4.1 为什么不直接按字数切块

医疗书籍的知识通常按章节组织。比如一个章节会完整讨论疾病、诊断、治疗、适应证、禁忌证或并发症。

如果直接按 1000 或 2000 字切块，会出现：

- 一个知识点被切到两个块里
- AI 看不到完整上下文
- 页面追溯时只能看到技术块，不知道来自哪一章
- 同一章节容易被重复提取出多个类似条目

所以当前实现使用章节优先策略，一章一条 `medical_knowledge_chunk`。

### 4.2 `normalizeChapterSegments` 做了什么

`normalizeChapterSegments` 是章节提取的核心方法。

它接收解析器产生的原始分段，然后按下面步骤处理：

1. 标准化标题：`normalizeSegmentTitle`
2. 从正文开头移除重复标题：`removeLeadingHeading`
3. 清洗正文：`cleanChapterContent`
4. 如果正文为空，跳过
5. 判断标题是否是目录、前言、绪言等无效章节：`shouldSkipSectionTitle`
6. 判断正文整体是否像目录页：`looksLikeDirectoryContent`
7. 判断正文是否像前言内容：`looksLikePrefaceContent`
8. 判断正文是否乱码过多：`containsMostlyGarbled`
9. 判断正文是否像教材编写说明：`looksLikeBookMetaContent`
10. 如果当前分段有有效章节标题，则结束上一章并开启新章
11. 如果当前分段没有标题，但已经处在某章内，则追加到当前章
12. PDF 场景下，如果开头没有章节标题，则丢弃无标题前置页
13. 最后将剩余内容构建为最终章节

这里有一个关键参数：`dropUntitledLeading`。

- PDF 调用时传 `true`
- TXT 和 DOCX 调用时传 `false`

原因是 PDF 前几页经常是封面、版权页、目录页、出版说明。它们常常没有真实章节标题，所以 PDF 会更激进地丢弃开头无标题内容。

### 4.3 `buildChunks` 做了什么

`buildChunks` 将清洗后的章节转换成数据库记录。

每个章节生成一个 `MedicalKnowledgeChunk`：

- `source_id`：来源书籍 ID
- `chapter_no`：章节序号
- `chapter_title`：章节标题
- `page_from`：起始页，PDF 场景下更有意义
- `page_to`：结束页
- `chunk_no`：块序号
- `raw_content`：原始章节内容
- `clean_content`：清洗后的章节正文
- `content_hash`：清洗正文的 SHA-256
- `token_estimate`：粗略 token 估计

`persistChunks` 入库前会先删除该来源下旧 chunk，再插入新 chunk，避免重新提取时混入旧章节。

## 5. 噪音清洗逻辑

### 5.1 噪音来源

医疗书籍导入后，常见噪音包括：

- 目录页
- 目录项，例如 `一、适应证................ 30`
- 多个目录项粘在同一行，例如 `四、呼吸性酸中毒......25 五、混合性酸碱平衡失调......`
- 前言、序言、绪言、绪论、导言
- 作者简介、内容简介、出版说明、再版前言
- 页码行，例如 `- 32 -`
- 版权说明
- PDF 抽取乱码
- 扫描/OCR 错误字符
- 同一页页眉页脚重复行
- 教材编写说明，例如某章由某某编写

这些内容如果不清掉，会造成两个问题：

- AI 会把目录和前言当正文抽取，生成低质量知识
- 规则兜底会把目录项当标题，产生置信度 50% 的垃圾条目

### 5.2 基础清洗 `cleanRawText`

`cleanRawText` 做的是基础文本规范化。

处理动作：

- 将 `\r` 替换成 `\n`
- 按行处理文本
- 每行调用 `cleanInlineText`
- 删除纯页码行
- 合并 3 个及以上连续空行
- 返回 trim 后的文本

它依赖两个正则：

- `PAGE_NUMBER_PATTERN`
- `BLANK_LINE_PATTERN`

这一步不会识别目录，也不会理解章节，只是把文本变得更适合后续逐行判断。

### 5.3 行内清洗 `cleanInlineText`

`cleanInlineText` 不使用预编译正则，但会调用：

```java
replaceAll("\\s{2,}", " ")
```

作用：

- 全角空格替换成普通空格
- tab 替换成普通空格
- 2 个及以上连续空白压成 1 个空格
- 去掉首尾空白

这个处理会影响标题识别。比如 `第 一 章`、`目   录`、`一、  适应证` 这类内容会先被压缩，再进入规则判断。

### 5.4 章节正文清洗 `cleanChapterContent`

`cleanChapterContent` 是章节正文的逐行过滤器。

它会对每行做判断，命中任意一种噪音就丢弃：

- `shouldSkipSectionTitle`：目录、前言、绪言等标题
- `isDirectoryLine`：目录项行
- `isBookMetaLine`：教材编写说明行
- `isGarbledLine`：乱码行
- `isCopyrightLine`：版权说明行

最后用 `seenLines` 去重。重复行通常来自 PDF 页眉、页脚、书名、章节名重复出现。

### 5.5 整段噪音判断

有些噪音不是单行能完全识别的，需要按整段判断。

`normalizeChapterSegments` 和 `buildSegment` 会调用：

- `looksLikeDirectoryContent`
- `looksLikePrefaceContent`
- `containsMostlyGarbled`
- `looksLikeBookMetaContent`

如果一整个分段被判断为目录页、前言页、乱码页或教材元信息页，就不会生成章节。

## 6. 正则表达式逐条说明

### 6.1 `HEADING_PATTERN`

代码：

```java
Pattern.compile("^(第[一二三四五六七八九十百零0-9]+[章节篇部分].*|[一二三四五六七八九十]+[、.].*|\\d+[、.].*)$")
```

用途：

判断某一行是否像章节标题。

能识别：

- `第一章 麻醉基础`
- `第2章 围手术期处理`
- `一、适应证`
- `二. 禁忌证`
- `1、诊断标准`
- `2. 治疗原则`

为什么需要它：

- PDF 逐页读取时，需要从页面文本里找章节标题
- TXT 和 DOCX 分段时，需要判断哪一行开启新章节

为什么还要配合其他判断：

目录项也可能长得像标题，例如 `一、适应证................ 30`。所以 `isHeading` 会额外要求：

- 长度不超过 60
- 不能是目录行
- 不能是前言、目录等跳过章节

### 6.2 `PAGE_NUMBER_PATTERN`

代码：

```java
Pattern.compile("^\\s*[—\\-]*\\s*\\d+\\s*[—\\-]*\\s*$")
```

用途：

识别纯页码行。

能识别：

- `12`
- `- 12 -`
- `— 12 —`
- `   12   `

为什么需要它：

PDF 抽取文本时，页码常常单独成行。如果不清理，AI 会看到大量无意义数字，关键词也可能被污染。

### 6.3 `BLANK_LINE_PATTERN`

代码：

```java
Pattern.compile("\\n{3,}")
```

用途：

把 3 个及以上连续换行压缩成两个换行。

为什么需要它：

PDFBox 抽取后的文本经常有大量空行，压缩空行能让后续按行处理更稳定，也减少 prompt 长度。

### 6.4 `DIRECTORY_LINE_PATTERN`

代码：

```java
Pattern.compile("^(第?[一二三四五六七八九十百零〇0-9]+[章节篇部分卷]|[一二三四五六七八九十百零〇0-9]+[、.．]).{1,100}?(\\.{2,}|·{2,}|…{1,}|\\s{2,})\\s*\\d{1,4}\\s*$")
```

用途：

识别最典型的目录项。

能识别：

- `第一章 麻醉基础................ 1`
- `第2章 围手术期处理...... 120`
- `一、适应证................ 30`
- `四、慢性疼痛........................ 50`
- `1. 诊断标准  35`

它拆开看是：

- 开头必须像章节编号或条目编号
- 中间有 1 到 100 个字符作为目录名称
- 后面有点线、省略号、连续空格等目录连接符
- 最后是 1 到 4 位页码

为什么需要它：

目录项最容易被误判为章节标题。这个正则就是为了把“有编号、有标题、有连接符、有页码”的行识别成目录，而不是章节。

### 6.5 `DIRECTORY_LEADER_PATTERN`

代码：

```java
Pattern.compile(".*(\\.{2,}|·{2,}|…{1,}|\\s{4,}).*")
```

用途：

识别目录连接符。

能识别：

- `......`
- `······`
- `……`
- 很长的空格间隔

它本身不代表目录，只说明这一行出现了目录常见的连接符。

为什么需要它：

有些 PDF 抽取出来的目录行不一定以页码结尾，或者多个目录项被粘在一行。单靠 `DIRECTORY_LINE_PATTERN` 不够，所以先用它判断是否存在目录连接符，再结合目录项开头或多目录项判断。

### 6.6 `DIRECTORY_ITEM_PREFIX_PATTERN`

代码：

```java
Pattern.compile("^(?:录\\s*)?(第?[一二三四五六七八九十百零〇0-9]+[章节篇部分卷]|[一二三四五六七八九十百零〇0-9]+[、.．]).*")
```

用途：

识别目录项的开头。

能识别：

- `第一章 麻醉基础`
- `第2章 围手术期处理`
- `一、适应证`
- `四、慢性疼痛`
- `录 四、呼吸性酸中毒`

为什么允许开头有 `录`：

PDF 抽取目录页时，`目录` 两个字可能断裂，后面的目录项会被抽成 `录 四、呼吸性酸中毒......`。这个规则就是为了覆盖这种抽取异常。

它通常和 `DIRECTORY_LEADER_PATTERN` 一起使用：

- 既有目录连接符
- 又像目录项开头
- 行长度不超过 140

满足这些条件才认定为目录行。

### 6.7 `MULTI_DIRECTORY_ITEM_PATTERN`

代码：

```java
Pattern.compile(".*[一二三四五六七八九十百零〇0-9]+[、.．].*[一二三四五六七八九十百零〇0-9]+[、.．].*")
```

用途：

识别一行里粘了多个目录项。

能识别：

- `四、呼吸性酸中毒......25 五、混合性酸碱平衡失调......`
- `1. 诊断标准......20 2. 治疗原则......22`

为什么需要它：

PDF 提取目录时经常丢掉换行，导致两个目录项出现在同一行。普通目录正则可能只匹配单个目录项，这个正则专门处理“多目录项粘连”的情况。

### 6.8 `SIMPLE_DIRECTORY_LINE_PATTERN`

代码：

```java
Pattern.compile("^.*\\s+\\d{1,4}\\s*$")
```

用途：

识别“文本 + 空格 + 页码”这类简单目录行。

但它不会单独决定一行是目录。代码还要求：

- 行长度不超过 40
- 内容包含 `章`、`节` 或 `篇`

能识别：

- `第一章 绪论 1`
- `第二节 麻醉管理 28`
- `上篇 基础知识 3`

为什么要加额外限制：

正文中也可能出现以数字结尾的句子。如果只看“末尾数字”，误杀会很多。所以代码要求短行且包含章节类关键词。

## 7. 非正则噪音规则说明

### 7.1 `SKIP_SECTION_TITLES`

内容：

```java
Set.of("目录", "目 录", "前言", "序言", "序", "绪言", "绪论", "引言", "导言", "作者简介", "内容简介", "出版说明", "再版前言")
```

用途：

这些标题对应的内容通常不是医学知识正文，应该整体跳过。

注意：

`shouldSkipSectionTitle` 使用 `contains` 判断，所以标题中包含这些词也会跳过。例如：

- `再版前言`
- `本书序言`
- `作者简介`

### 7.2 `looksLikePrefaceContent`

用途：

判断正文开头是否像前言类内容。

识别开头：

- `前言`
- `序言`
- `绪言`
- `绪论`
- `目录`

为什么需要它：

有时解析器没有把 `前言` 识别成标题，但正文第一行就是 `前言`。这时仍然需要整段跳过。

### 7.3 `looksLikeDirectoryContent`

用途：

判断一整段内容是否主要由目录项组成。

当前判断逻辑：

- 统计有效行数
- 统计目录行数
- 如果目录行不少于 3 行，且目录行占比达到 45%，认为整段是目录页
- 如果有效行数不超过 3 行，且有目录行占比达到 50%，也认为整段是目录页

为什么需要它：

单行目录可以在 `cleanChapterContent` 里删掉，但有些目录页清理后仍可能残留少量行。整段判断可以防止目录页被保存成章节。

### 7.4 `isBookMetaLine`

用途：

识别教材编写说明。

当前判断逻辑：

- 行长度不超过 160
- 包含 `编写`
- 出现至少两个 `第`
- 包含 `章` 或 `节`

能识别：

- `第七章围手术期处理由李先强编写;第八章外科患者的营养代谢由某某编写`

为什么需要它：

这类内容不是医学正文，但很容易被 AI 抽成知识条目，比如“第七章由谁编写”。所以要提前过滤。

### 7.5 `looksLikeBookMetaContent`

用途：

判断一整段是否主要由教材编写说明组成。

当前判断逻辑：

- 统计有效行数
- 统计命中 `isBookMetaLine` 的行数
- 命中比例达到 50% 时，整段跳过

### 7.6 `containsMostlyGarbled`

用途：

判断一段内容是否乱码占比过高。

当前逻辑：

- 忽略空白字符
- 统计有效字符数量
- 统计不在允许字符集合里的字符数量
- 如果异常字符占比大于等于 35%，认为是乱码

允许字符包括：

- 字母
- 数字
- 中文 CJK 字符
- 常见中文标点
- 常见英文标点
- 医学表达中常见符号，例如 `%`、`+`、`=`、`<`、`>`

为什么需要它：

PDF 或 OCR 解析失败时，可能出现大量不可识别字符。如果不清理，AI 会浪费 token，还可能生成无意义内容。

### 7.7 `isGarbledLine`

用途：

判断单行是否乱码。

当前逻辑：

- 整行满足 `containsMostlyGarbled`
- 或包含替换字符 `�`

`�` 通常表示解码失败。

### 7.8 `isCopyrightLine`

用途：

识别版权和禁止转载说明。

当前识别：

- 以 `版权所有` 开头
- 以 `Copyright` 开头
- 包含 `未经许可不得`

## 8. AI 提取流程

### 8.1 按章节提取

章节块入库后，`extractKnowledgeItems` 会遍历每个 `MedicalKnowledgeChunk`。

每个 chunk 调用 `extractFromChunk`。

给 AI 的输入包括：

- 书籍名称
- 章节标题
- 清洗后的章节正文

提示词要求 AI：

- 只返回 JSON
- JSON 格式固定为 `{"items":[...]}`
- 每章提取 1 到 5 条知识
- 每条知识包含 `itemType`、`title`、`keywords`、`department`、`summary`、`content`、`confidenceScore`
- 如果没有有效医学知识，返回空数组

### 8.2 模型返回解析

`parseKnowledgeResult` 负责解析模型结果。

处理方式：

1. 从模型回答中找到第一个 `{` 和最后一个 `}`
2. 截取 JSON 文本
3. 用 fastjson2 解析
4. 读取 `items`
5. 转换成内部 `ExtractedKnowledge`
6. 过滤标题或正文为空的结果

### 8.3 AI 失败时的兜底

如果出现以下情况，会走 `buildFallbackKnowledge`：

- AI 调用超时
- AI 调用异常
- AI 返回空结果
- AI 返回结果不是合法 JSON
- JSON 中没有有效知识条目

兜底逻辑：

- 类型固定为 `知识点`
- 标题优先取正文中的标题，其次取章节标题
- 摘要取清洗正文前 120 字
- 正文取清洗正文前 500 字
- 科室固定为 `综合`
- 置信度固定为 `0.50`

所以如果页面上看到大量置信度 50% 的条目，通常说明 AI 没成功提取，或者前置清洗后的内容仍然不适合模型提取。

## 9. 知识入库和证据入库

### 9.1 知识条目入库

AI 提取出知识后，系统调用 `buildKnowledgeItem` 创建 `medical_knowledge_item`。

主要字段：

- `source_id`：来源书籍
- `item_type`：知识类型
- `title`：标题
- `keywords`：关键词
- `department`：科室
- `summary`：摘要
- `content`：正文
- `structured_data`：结构化 JSON
- `confidence_score`：置信度
- `dedup_key`：去重键
- `review_status`：审核状态

### 9.2 去重和合并

`dedup_key` 由下面内容生成：

- 来源 ID
- 标题
- 知识类型
- 科室

同一轮提取中，如果重复出现相同 `dedup_key`：

- 合并关键词
- 保留更长正文
- 保留更长摘要
- 保留更高置信度
- 更新结构化 JSON

### 9.3 证据引用入库

每条知识会调用 `ensureItemReference` 关联章节证据。

写入表：`medical_knowledge_item_ref`。

主要字段：

- `knowledge_item_id`：知识条目 ID
- `chunk_id`：章节块 ID
- `quote_text`：引用片段
- `sort_order`：排序

证据引用的价值是让前端详情页可以展示这条知识来自哪本书、哪一章、哪段原文。

## 11. 当前规则的边界

当前章节提取和清洗主要基于规则和正则，不是完美的文档结构解析。

容易出问题的场景：

- PDF 本身是扫描件，文本来自 OCR，错字很多
- 目录页格式非常特殊，没有点线、页码或明显编号
- 正文里的小节标题和目录项长得非常像
- 一页里混合目录、前言和正文
- 医学公式、特殊符号很多，可能被误判为乱码
- 章节标题被 PDFBox 拆成多行

如果后续继续优化，建议方向：

- 在导入前保存一份“解析预览”，让用户确认前几章是否正常
- 给 `medical_knowledge_chunk` 增加清洗状态和噪音命中原因
- 将目录规则、前言规则、乱码阈值配置化
- 增加人工删除章节块或重新归并章节的能力
- 引入 PDF 目录书签解析，如果 PDF 内置 outline，可以优先使用 outline
- 对置信度 50% 的兜底条目单独标记，前端默认隐藏或进入待审核区
